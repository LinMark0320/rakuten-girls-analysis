# 0001. 混合式資料獲取架構與本機 SQLite 儲存

## Context
我們需要針對 27 位樂天女孩在籍主要成員，跨平台（Yahoo拍賣、Facebook社團等）獲取近三年歷史成交紀錄與即時競標商品。
Yahoo 拍賣具備公開商品網址與結標資料，可全自動爬取；而 Facebook 社團多為封閉式或存在反爬蟲登入驗證，全自動模擬登入爬蟲有極高的帳號封禁風險與維護成本。

## Decision
我們決定採用「雙軌混合獲取模式」搭配本機 SQLite 資料庫：
1. **Yahoo 拍賣**：採用 Python 自動化爬蟲模組，直接對接公開搜尋與商品 API，全自動獲取在線競標與結標歷史。
2. **Facebook 社團**：
   - ~~針對公開社團貼文：透過搜尋引擎公開快取索引（Google site:facebook.com 檢索）獲取結構化片段。~~
     **【2026-09-17 作廢】** 已實際測試 Google、Bing、DuckDuckGo 三家對 `site:facebook.com "樂天女孩" "{成員}" (售 OR 成交 OR ...)` 的無登入、無 JS 執行的純 HTTP 請求：
     - Google：回傳 HTTP 200，但內容是空殼頁面，沒有任何 `<h3>` 搜尋結果區塊，唯一出現 "facebook" 字樣處只是把查詢字串原樣印回，並非真實結果。
     - Bing：抓到的 2 個 facebook.com 連結經檢查皆為 Bing 自身頁面的 UI 連結（搜尋框、快取連結），並非貼文結果。
     - DuckDuckGo：回傳 HTTP 202（非正常 200），頁面僅 14KB，明顯是異常流量偵測攔截後的簡化頁面。
     三家皆對無瀏覽器指紋、無 cookie、無 JS 執行的請求做了防爬處理，**連結果都拿不到**，而非「拿得到但品質差」。結論：此路線技術上不可行，正式棄用，不再規劃投入。
   - 針對非公開/社團內貼文：在前端儀表板提供「一鍵貼上智慧解析器（Paste & Parse）」，將使用者複製的貼文文字自動提取出成員、卡種、成交金額並寫入庫。**（2026-09-17 起，此為 Facebook 資料的唯一獲取管道。）**
3. **資料儲存**：後端採用本機 SQLite 資料庫（`cards.db`），依據各平台唯一商品 ID 實施去重與出價歷史追蹤，並定期導出純 JSON 供前端 `index.html` 即時載入。

## Consequences
- **優點**：兼顧 Yahoo 拍賣的全自動化爬取效率，同時完全免除 Facebook 帳號被封鎖的風險；SQLite 確保數據不遺失、不重複，且易於擴展。
- **取捨**：Facebook 社團（不論公開或非公開）的交易紀錄，經實測驗證無法透過搜尋引擎自動化取得，完全仰賴賣家在社團看到後一鍵貼上解析；這是既有限制而非暫時性缺口。
